# Creator validation: one task, one correction, one decision

[← Evidence and next experiments](review-guide.md) · [Engineering handoff](handoff-template.md)

**This is a plan and blank record, not completed research.** Begin with one relevant creator, then repeat with a small set of creators if the task is useful. Ask about a recent real job before presenting the tool: what they needed to deliver, where revision became difficult, and how they solved it. Separate that account from assumptions made by the prototype designer.

## Agree on the task before the session

- Select one case's bounded task and authorized source material. Write the intended visual message, required format and creative quality criteria.
- Record the exact hosted/local version. A result from a local adaptation does not validate another deployment.
- Ask the creator to describe their current workflow and baseline. Where feasible, compare the same source and brief; record task order and familiarity because learning can affect time.
- Let the creator attempt the prototype without coaching. Log help when it becomes necessary. Ask them to change one part while preserving a choice they already like.
- Review the encoded output together. Count correction work and quality failures as part of the task, not just generation time. Do not trigger paid processing without a separate agreed scope and budget.

## Session record

| Field | Complete with observed evidence |
| --- | --- |
| Participant and context | Relevant production experience; permission for any quote or recording |
| Actual workflow problem | Recent task, existing workaround and consequence; distinguish the creator's account from inference |
| Hypothesis and minimum task | One expected benefit and the smallest output that can test it |
| Inputs and version | Authorized fixture, tool/URL, revision, browser and relevant settings |
| Baseline | Existing workflow and result, or **not observed** |
| First attempt | Completion, first hesitation, help given and abandoned steps |
| Local correction | Requested change; what had to remain fixed; affected controls; unintended changes |
| Time and rework | Active editing, waiting, retries, correction time and interruptions; leave unknowns blank |
| Output checks | Decode/duration/dimensions plus the case's visual criteria; **pass / fail / not checked** |
| Creator assessment | What was useful, what was confusing, what they would still do elsewhere; quote only actual feedback |
| Evidence | Source/output identifiers, comparison frames and permitted recording link |
| Decision | Expand, iterate, stop or narrow; why; next owner and experiment |

## Use the result to choose the next build

**Expand** to the next input class only when the core task and the local correction succeed without critical help, and the delivered output passes the agreed checks. Confirm that the creator values the task; task completion alone does not establish demand.

**Iterate** the specific failure: for example, an undiscoverable import action, a crop that cannot be corrected independently, an ambiguous control, or an export that differs from the preview. Keep the next build tied to that observation.

**Stop or narrow** an approach when it repeatedly damages meaning or structure, cannot recover the intended subject, or adds more correction than it removes. Preserve any useful manual controls. A stopped automation idea does not mean discarding the entire project.

Hand engineering the accepted task, reproducible fixture, actual failure, state/control mapping and verification result. Do not turn an unrun plan into a case-study outcome.
